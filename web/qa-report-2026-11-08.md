## WEB-01 — Signed-in API calls always return 401 (P0)

### Symptom

- Clicking **Read later** or **Mark important** shows:
  `Could not save (401). Try again in a moment.`
- Starring a topic shows:
  `Could not update your follows (401). Try again in a moment.`, and the star silently reverts.
- **Library** always says *"Nothing saved yet."*; the notes panel always says *"Nothing tracked yet."*
- The header never shows the account email, and the admin "Run the pipeline now" button never appears.

### Reproduction

1. Sign in (any account), open `/feed`.
2. Click **Read later** on any card.
3. Error banner appears; nothing is saved.

Direct check, from the browser console on the live site:

```
fetch('/api/me').then(r => r.status + ' ' + r.text())
// → "401 {"error":"sign in required"}"
```

Every private endpoint behaves the same:

| Endpoint | Status | Body |
|---|---|---|
| `GET /api/me` | 401 | `{"error":"sign in required"}` |
| `GET /api/my/library` | 401 | `{"error":"sign in required"}` |
| `GET /api/my/notes` | 401 | `{"error":"sign in required"}` |
| `GET /api/my/follows` | 401 | `{"error":"sign in required"}` |

`window.Clerk.user` is set (`user_3LiY2…`, `badrbajamil1@gmail.com`), the `__session`
cookie is present, and calling `Clerk.session.getToken()` returns a valid RS256 JWT:

```
iss: https://funny-fly-4667.clerk.accounts.dev
sub: user_3LiY2EvXMxM4BjC96VUG5wF0Bcj
azp: https://synthetic-data-web.coolbadrtv1.workers.dev
```

So it is **not** a missing session, a cookie issue, or a client that forgot the header.
Sending the token by hand fails too:

```js
const t = await Clerk.session.getToken()
fetch('/api/me', { headers: { authorization: 'Bearer ' + t } })
// → 401 {"error":"sign in required"}
```

`CLERK_SECRET_KEY`, `CRON_RUN_TOKEN` and `OPENROUTER_API_KEY` are all present on the
deployed Worker (`wrangler secret list`), so the secret is not missing either.

### Root cause

`web/worker/auth.ts:29-36`:

```ts
let payload: ClerkJwt
try {
  payload = (await verifyToken(token, { secretKey: env.CLERK_SECRET_KEY })) as ClerkJwt
} catch {
  return null
}
const userId = typeof payload.sub === 'string' ? payload.sub : ''
```

In `@clerk/backend` **3.27.0** (the version in `web/package.json`), `verifyToken()` does
not return the payload. It returns a result object:

```ts
// node_modules/@clerk/backend/dist/jwt/types.d.ts
export type JwtReturnType<R, E> =
  | { data: R; errors?: undefined }
  | { data?: undefined; errors: [E] }
```

The implementation confirms it (`dist/tokens/verify.ts`, compiled):

```js
async function verifyToken(token, options) {
  const { data: decodedResult, errors } = decodeJwt(token)
  if (errors) return { errors }
  ...
  return await verifyJwt(token, { ...options, key })   // → { data } | { errors }
}
```

So `payload` is actually `{ data: { sub, iss, … } }`, `payload.sub` is `undefined`,
`userId` becomes `''`, and `currentViewer()` returns `null` on **every** request.
The `as ClerkJwt` cast is what hides this from TypeScript.

### Fix

```ts
let verified
try {
  verified = await verifyToken(token, { secretKey: env.CLERK_SECRET_KEY })
} catch {
  return null
}
if (verified.errors || !verified.data) return null
const userId = typeof verified.data.sub === 'string' ? verified.data.sub : ''
if (!userId) return null
```

Then keep the rest as-is (`payload` → `verified.data` where the email is read).

Worth adding: a unit test that stubs `verifyToken` with the real return shape
(`{ data: { sub } }`), because this class of bug passes typecheck thanks to the cast.

### Impact

Everything behind Clerk is unavailable to every user, in every browser. Nothing is
written to D1, so no data is corrupted — the features are simply dead.

## WEB-02 — Header nav overflows and hides Archive on phones (P1)

### Symptom

At phone widths the nav runs past the right edge and is clipped by
`overflow-x-clip` on the root. The last item (**Archive**) and the Clerk user button
are outside the viewport and cannot be tapped. There is no hamburger menu.

### Reproduction

Open the site at 390 px wide (or with the review pane narrow) and look at the header.

Measured at `window.innerWidth = 390`:

| Element | x | right edge | Visible |
|---|---|---|---|
| Feed | 223 | 282 | yes |
| Brief | 284 | 343 | yes |
| Library | 345 | 416 | **clipped** |
| Archive | 418 | 492 | **no** |
| User button | — | 524 | **no** |

The nav starts fitting only around **600 px**:

| Viewport | Archive right edge | Fits |
|---|---|---|
| 390 | 492 | no |
| 430 | 492 | no |
| 449 | 492 | no |
| 600 | 533 | yes |

The page itself does not scroll horizontally (`overflow-x-clip`), so there is no way to
reach the hidden links by scrolling.

![Mobile header: Library clipped, Archive and avatar off-screen, plus a stuck 401 banner](C:\Users\badrf\.t3\userdata\browser-artifacts\browser-screenshot-synthetic-data-web-coolbadrtv1-workers-d-mw7pt71y-eff1753d.png)

### Root cause

`web/src/App.tsx:262-298`: the header is a single non-wrapping flex row
(`flex items-center justify-between`) with four nav links plus `UserButton`, and no
breakpoint that collapses it (the only responsive classes are `sm:` spacing tweaks).

### Fix options

- Hide the link row below `md` and add a menu button that opens the four links.
- Or `overflow-x-auto` the nav as a stopgap (makes Archive reachable, ugly but honest).

## WEB-03 — Error banners never clear on navigation (P1)

### Symptom

An error raised on one page is still on screen after you navigate somewhere else.
Example: get the 401 on `/feed`, click **Archive** — the Archive page shows
*"Could not update your follows (401)"* above content that has nothing to do with it.

### Reproduction

1. On `/feed`, star a topic (fails with 401).
2. Click **Archive** in the nav (SPA navigation, no reload).
3. The red banner is still there.

### Evidence

```
path: /archive
role=alert: "Could not update your follows (401). Try again in a moment."
```

A full page reload clears it, which is why it feels random.

### Root cause

`followError` and `libraryError` live in `App` state (`App.tsx:65,68`) and are rendered
inside every page (`App.tsx:301`, `FeedPage.tsx:223`, `BriefPage.tsx:176`,
`LibraryPage.tsx:52`). Nothing resets them in the route-change effect
(`App.tsx:244-252` handles scroll and focus only), and there is no dismiss control.

### Fix

Clear both in the route-change effect:

```ts
useEffect(() => {
  setFollowError(null)
  setLibraryError(null)
  ...
}, [route])
```

and/or render them with a dismiss button. Keep them across Clerk re-auth if you want,
but not across page changes.

## WEB-04 — Signed-in user still sees "Sign in to your feed" (P2)

`/` (landing) always renders the primary CTA *Sign in to your feed*
(`LandingPage.tsx:62-65`), even when Clerk already has a user — confirmed with
`window.Clerk.user` set. Clicking it opens the Clerk sign-in modal for an account that is
already signed in. Suggest swapping it for **Go to your feed** when signed in (the
logo and nav already link to `/feed`).

## WEB-05 — Duplicate source labels split the same source in two (P2)

`GET /api/archive/counts` returns:

```json
"sources": [
  { "label": "GitHub", "count": 3 },
  { "label": "arXiv",  "count": 2 },
  { "label": "news",   "count": 2 },
  { "label": "arxiv",  "count": 1 },
  { "label": "github", "count": 1 },
  { "label": "Hacker News", "count": 1 },
  { "label": "remio.ai", "count": 1 }
]
```

The **My topics → Sources** panel renders these raw, so a user sees `GitHub 3` and
`github 1` as separate rows. Starring `github` will not include the `GitHub` items
(matching is exact). The brief page title-cases these for display, which hides the
problem there but does not merge them.

Cause: the collector/pipeline writes both the collector key (`github`, `arxiv`, `news`)
and a display label (`GitHub`, `arXiv`) into `items.source`, depending on the run.

Fix: normalise on ingest (lower-case key + display label in one place), and group
counts case-insensitively until old rows are migrated.

## WEB-06 — Public pages are gated behind Clerk (P2)

`App.tsx:238`:

```ts
const identityPending = !isLoaded || (needsIdentity && !sessionChecked)
```

`!isLoaded` is true for **all** routes, so `/archive` and `/brief/<week>` — which need no
identity at all — show only *"Loading your session…"* until Clerk's JS loads. On a cold
load this is visible for a moment; with an extension or network that blocks
`*.clerk.accounts.dev` it is permanent, and the public archive/brief become unreadable.

Suggestion: only gate on `isLoaded` for `/feed` and `/library`; render the public pages
immediately.

## WEB-07 — 401 is rendered as "empty", not "error" (P3)

`getJson()` returns `null` on 401 (`src/lib/api.ts:38`), and callers treat `null` as
"no data": the Library page says *"Nothing saved yet."* for a signed-in user whose library
simply failed to load. Once WEB-01 is fixed this becomes rare, but the ambiguity is worth
removing — a 401 while Clerk says "signed in" should surface, not silently look empty.

## WEB-08 — "Open the PDF" leaves the SPA (P3)

`BriefPage` renders `<a href="/api/reports/<week>/pdf">` with no `target`. Clicking it
navigates the tab to the PDF; the app state is gone and Back is the only way out. It works
(200, `application/pdf`, ~61 KB) — it just feels like a dead end. Add
`target="_blank" rel="noopener"`, or a download attribute.

## WEB-09 — Unknown paths return 200, and the document title never changes (P3)

- `GET /does-not-exist` → **200** `text/html`; `GET /brief/week-1999-01-01` → **200**.
  The in-app 404/"brief does not exist" screens are correct and friendly, but the status
  code is wrong for crawlers and uptime checks (`wrangler.jsonc` uses
  `not_found_handling: "single-page-application"`, which forces 200).
- `document.title` is `Well7 Research Lab — Synthetic Data Weekly` on every route, so
  browser history and tabs cannot tell pages apart. Set it per route.

## WEB-10 — Filter counts ignore the active search (P3)

With a search query active, the section pills still show their unfiltered counts:
searching "differential privacy" on the 6 Nov brief shows **Worth a look 1** but the list
renders *"Nothing matches these filters."* Either count after the search is applied, or
label the counts as week totals.

## What works (baseline for regressions)

Verified live, all on a cold load unless noted:

- Routes render and settle in ~0.6 s: `/`, `/feed`, `/library`, `/archive`, `/brief`
  (redirects to the newest week), `/brief/week-2026-11-06`, `/brief/week-2026-11-01`.
- `/brief` redirect uses `replace`, so Back does not bounce.
- Unknown route → "This page does not exist." screen with working links.
- Unknown week → "This brief does not exist." screen with a link to the archive.
- Data endpoints: `/api/reports`, `/api/reports/<id>`, `/api/reports/<id>/items`,
  `/api/archive/counts` → 200; PDF for both weeks → 200 `application/pdf`.
- Both weeks appear in the archive, oldest → newest, and open correctly.
- Search filters the feed (7 → 2 items for "differential privacy").
- Section tabs (All / Top picks / Tools / Worth a look) filter correctly.
- No uncaught JS errors or rejected promises were recorded during the whole walkthrough.
- SPA nav leaves no horizontal overflow on content at 390 px — only the header (WEB-02).

## Suggested order

1. **WEB-01** — one-line destructure in `worker/auth.ts`; unblocks every personal feature.
2. **WEB-03** — clear error state on route change (small, removes the "random error" feel).
3. **WEB-02** — mobile header; makes Archive reachable on phones.
4. WEB-05, WEB-06, WEB-04, then the P3s.
